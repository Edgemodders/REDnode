## Conventions

- **Commits:** commit straight to `main` and push, in small logical commits. Agree the plan in chat first. Use a PR only for large or risky changes, and ask before opening one.
- **Versions:** REDnode has one version, shared by the plugin, the overlay host, the `rednode` package, the UI kit and the built-in apps, in `VERSION` at the repo root (agreed with the user on 2026-10-13, ahead of a release bundle). Change it only with `node tools/version.mjs <version>`; the plugin's build reads `VERSION`, and `tools/build-native.ps1` stops if a part differs. Raise it with each in-game test build, and refer to it as "REDnode <version>". Sample packages keep their own versions. The parts are listed on the docs home page, "What REDnode is made of".
- **Release gate (the owner's rule, 2026-10-17):** no release (Make a release, `npm run release`, a Nexus upload) until the owner has finished every in-game test of what goes into it. Every test in docs/testing.md for the builds since the last release must have passed in game; anything not yet tested, or failed, stops the release. Check this and say what is still open before starting a release run, even when asked to release.
- **Releases:** the player zip (`npm run release:zip`, `tools/release/player-zip.mjs`) holds the plugin, the packaged host and the samples in `SAMPLES`, laid out as `red4ext/plugins/REDnode/`. The **Release zip** workflow builds it on a manual run (artifact); with **Make a release** ticked it also tags `v<VERSION>` and makes the GitHub release. REDbridge and REDagent are not in it. The workflow also builds every app pack in `packs/` (`npm run release:pack -- --all`) and attaches each zip to the release, with a line in the notes from its `pack.json` (agreed with the user on 2026-10-20); a pack with changes under **Unreleased** in its changelog stops the run, so raise its version and release its changelog first. The Nexus page (not live: see nexus/README.md) has its source in `nexus/description.bbcode`; its form fields and update steps are in `nexus/README.md`.
- **Changelog (the owner's rule, 2026-10-19; the same convention in every Edgemodders repo):** `docs/changelog.md` has a section per release, newest first, with **Unreleased** on top. With each change a player or modder would notice, add a line under **Unreleased** in the same commit, grouped **New**, **Changed**, **Fixed**, **Other**; leave out test-only changes. Before a release, rename **Unreleased** to `## <version> (<date>)` and start a new empty one. The release workflow takes the GitHub release notes from that section and stops if there is none (`tools/release/notes.mjs`). The same section goes into the Nexus page's changelog for that version: `npm run release:notes -- --nexus` prints it as plain lines.
- **Git identity:** set per repo to `CyberbuildsAI` with the GitHub no-reply email (see dev-setup). Never change the global identity.
- **Never commit game files** or data extracted from them: DLLs, archives, scripts, assets, TweakDB, raw RTTI dumps (`rtti-dump*`). `.gitignore` covers the common cases.
  - **One exception, agreed with the user on 2026-10-11:** `gameapi/<game version>/rtti.json` holds base-game type signatures (names, types, flags, enum values) for the published game API reference, like NativeDB. Produce it only with the REDnode dumper on a base-game run and import it with `npm run gameapi:import`. Nothing else from the game goes in.
- **Shared theme:** the REDnode HUD VS Code theme lives in [REDcode](https://github.com/Edgemodders/REDcode) at `extensions/rednode-hud-theme` (package `edgemodders.rednode-hud-theme`). The copy that used to be in `tools/vscode-theme` here was removed on 2026-10-11; edit the theme in REDcode only.
- **Writing style:** plain, short sentences. Tables for comparisons and lists of facts. Use the design doc's terms: Tier 1 (sync interceptors, in-process), Tier 2 (async Node mods, out of process), declarative rules, phases P0 to P4, and the `rednode` package name. Mark anything unverified as unverified.

## Docs site

- `docs/` is published by GitHub Pages at https://edgemodders.github.io/REDnode/. It is the human-facing documentation, so it must look polished.
- `.github/workflows/pages.yml` builds and deploys the site on every push to `main`: TypeDoc generates the API reference into `docs/api`, `tools/gameapi/build.mjs` generates the game API reference into `docs/game`, `tools/examples/build.mjs` generates the example apps section into `docs/examples`, then Jekyll renders `docs/`. Never commit `docs/api`, `docs/game` or `docs/examples`.
- **Example apps** (`docs/examples`, asked for by the user on 2026-10-18): a page per app in `packages/overlay/apps` with a live preview and its files with copy buttons. The text is in `tools/examples/notes.mjs`: add an entry for every new app. Previews run the real code against a simulated game in `docs/assets/examples/sim/` (`rednode.js` for pages and as the host, `worker.js` as the package inside a Node mod's Web Worker, `runner.js` drawing ui-builder windows and copying the host's crash, restart and not-responding rules). When the `rednode` package or `window.rednode` gains what an app uses, add it to the simulation. Check locally with `npm run docs:examples` and `npm run docs:serve` (http://127.0.0.1:4000/examples/).
- The `rednode` package's game API types (`packages/rednode/src/generated/`) are generated from `gameapi/<version>/rtti.json` by `tools/gameapi/types.mjs` during its build. Never commit them.
- The game API reference is REDnode's own ground truth for game types. Its descriptions live in `gameapi/notes/<NativeName>.md` (format in `gameapi/notes/README.md`). When a test shows how a game type behaves, add or update its note. `npm run docs:game` builds it locally, about a minute.
- Give every exported symbol in `packages/rednode/src` a TSDoc comment with an `@example` where it helps. That is the source of the API reference.
- Write docs as markdown in `docs/`. Jekyll renders them with the HUD layout (`docs/_layouts/default.html`, `docs/assets/css/hud.css`). Add every new page to `nav` in `docs/_config.yml`.
- `docs/design.html` is a standalone, hand-written page and must stay a complete HTML document.
- Long-term goal: a rich, navigable docs site with a full API browser. Offline browsing (shipping the built site) is a later concern.
