REDnode

REDnode is a Node-based API for scripting Cyberpunk 2077, built on the same injection points that RED4ext, Cyber Engine Tweaks and redscript already use. Asynchronous mods run in a normal Node process. A small sandboxed tier runs inside the game for the few cases that must change a value mid-call.

Recommended: hybrid B + small A Tier 2: Node (out of process) Tier 1: sandboxed in-process Single-player modding

01Goal and scope

In scope
  • Let modders write game logic in TypeScript and JavaScript with npm packages.
  • Expose game state, events and commands through a typed API generated from the game's own reflection data.
  • Coexist with CET, RED4ext plugins, redscript and REDmod.
  • Survive game patches without per-patch rewrites of mods.
Out of scope for v1
  • Multiplayer or anything that touches online services.
  • Full in-process Node with fs, require and a live event loop.
  • Replacing redscript for engine-level changes.
  • Mods that need to run arbitrary game calls from inside a hook.

What this teaches

  • The game exposes a reflection (RTTI) system. That is what makes a dynamic scripting layer possible, and CET relies on it.
  • Codeware is a native RED4ext plugin that exposes extra functions to redscript. A native bridge exposing a scripting surface is the established pattern.
  • RedData and mod_settings ship a native DLL together with .reds files. Mod authors already expect that packaging shape.

03Options considered

PlanApproachStrengthsWeaknesses
AEmbed Node in a RED4ext plugin or .asi.Closest to CET. JS runs inside hooks as plain function calls.30 to 80 MB runtime. Event loop and threads inside a DX12 game process. Hard to keep stable.
BThin native RED4ext plugin plus a separate Node process over IPC.Crash isolation. Normal npm tooling. Easy hot reload. Small native surface to maintain.No synchronous access from hooks. Round-trip latency on every call.
CEmbed QuickJS only.About 1 MB. Fast start. Easy to sandbox.Not Node. No npm ecosystem.

The tradeoff in Plan B

A hook runs inside the game's own function call, on the game thread, and the game waits for it to return. If the logic lives in another process, the hook must block on a round trip. That costs roughly 50 to 200 µs when healthy and much more when Node is busy. A 60 fps frame has about 16 ms, and hooks such as damage or per-frame ticks can fire thousands of times a frame. If the Node process crashes or hangs, the game thread blocks until a timeout.

PatternPlan B
Notify: "the player took damage"Works. The hook enqueues an event and returns.
Query: "what is the player's health?"Works. Node awaits the answer.
Command: "set health to 100"Works. Queued and applied on the game thread next tick.
Intercept: change a value before the call continuesDoes not work well. Needs a synchronous answer while the game waits.

Keep Plan B as the main path. Add a small in-process tier for interceptors only. A mod can ship either tier or both.

Tier 1 · sync interceptors
  • Runs inside the hook on the game thread.
  • Can change arguments or return values, or cancel a call.
  • No await, no I/O, no require.
  • Hard time budget, for example 100 µs.
Tier 2 · async Node mods
  • Observe events, query state, send commands.
  • Full Node and npm.
  • Never blocks the game.
  • Can push parameters to Tier 1 interceptors.

What runs Tier 1

Full Node / V830 to 80 MBBrings back every problem of Plan A. Not recommended for interceptors.

QuickJSabout 1 MBRecommended. Small, easy to sandbox and to time-limit. TypeScript is compiled ahead of time. Slower than V8, which is fine for tiny functions.

Tier 1 shares TypeScript types with Tier 2 but is not Node. The documentation must say so plainly.

Cheaper than either: declarative rules

For the simplest cases, such as "multiply incoming damage by X", offer a no-code rule that the native plugin applies directly in the hook. It needs no JS engine and no IPC, and it covers a large share of real mods.

05API sketch

Tier 1 · interceptor (sync, sandboxed)
export default defineInterceptor({
  target: "PlayerPuppet.OnDamageReceived",
  run(ctx) {
    ctx.args.damage *= ctx.params.multiplier;   // pushed from Tier 2
  }
});
Tier 2 · async mod (full Node)
import { game } from "rednode";

game.on("PlayerPuppet.OnDamageReceived", async (e) => {
  await db.log(e);                          // fine, the game is not waiting
  game.player.setHealth(100);              // queued, runs next tick
});

const hp = await game.player.getHealth();    // async query
interceptor("damage-scale").set("multiplier", 0.5);

Native plugin responsibilities

  • Enumerate RTTI classes, functions and properties for type generation.
  • Call functions and get or set properties on game objects.
  • Hook functions through RED4ext and the Address Library so mods survive patches.
  • Marshal game types (CName, Vector4, handles, arrays) to and from JSON-like values.
  • Queue all incoming commands and run them on the game thread, because game objects are not thread-safe.
  • Manage object handle lifetime so Node never holds a stale reference.

06Native game UI (ink)

Proposed on 2026-10-18, not scheduled. The game draws its own UI with ink: a tree of widgets (inkCanvasWidget, inkTextWidget, inkImageWidget and so on) with logic controllers for behavior (inkButtonController, inkSliderController and so on). redscript mods build their menus and HUD parts into that tree. REDnode should let JavaScript and TypeScript mods do the same, with a set of tags and an ink API in the rednode package.

What REDnode has today

Neither of REDnode's two UI paths is ink. Overlay apps write HTML, and the ui builder lets Node mods describe a window as a tree of nodes. Both are drawn by Chromium in the overlay host, and the plugin composites the picture over the game's frame. The game's UI never sees them. The "Native button" sample is an HTML window styled like the game, not ink.

Overlay (HTML apps, ui)Ink (proposed ink)
Drawn byChromium offscreen; the plugin composites it over the frameThe game's renderer, inside its own UI
LookThe REDnode UI kit, or any web contentThe game's fonts, styles and library widgets
HUD hiding, photo mode, UI scale, HDRREDnode follows them by hand (the HUD widget rules)Follows them as the game's own UI does, by layer (unverified)
InputF10 Using mode with REDnode's cursorThe game's cursor in menus; none on the HUD in gameplay (open question)
CostA Chromium process and its texturesWidgets in the game's tree, no extra process
ReachAnything a web page can doInk widgets and the game's library items only

The generic game API (rtti.call, api in the package) can already call ink functions one at a time. inkCompoundWidget.AddChild returns a reference, and SetText works on it. With Codeware, a Node mod could reach the HUD layer and add raw widgets. That is unverified: nobody has tried it. Five things are missing: a root to attach to without Codeware, events, ownership and cleanup, a rebuild after a save load, and speed. Each call is one round trip, and a styled panel of 40 widgets takes hundreds of calls.

Which tier

Neither Tier 1 nor a new engine in the game is needed. The work splits between the native plugin and Tier 2:

Plugin · the ink driver (native, in process)
  • Keeps each package's tree, so it can rebuild it after a save load or a HUD rebuild with no help from Node.
  • Applies changes in batches on the game thread, between frames, with a budget per frame.
  • Owns the widgets, and removes a package's widgets when the package stops.
  • Registers callbacks through a small listener class in REDnode's scripts and sends the events out.
  • Reads bindings each frame, so a value that changes every frame needs no round trip.
Tier 2 · the ink API (Node, TypeScript)
  • Tags and functions that describe a tree, typed.
  • Diffs each new tree against the last one and sends only the changes.
  • Runs the mod's handlers for clicks, hovers and value changes.
  • Hot reload, like the rest of Tier 2.

UI needs very few synchronous answers. Wherever the game would wait, the answer can be declared in the tree ahead of time, the same way Tier 2 pushes parameters to an interceptor:

NeedHow it works without a synchronous call
Build or change the UICommands, batched and applied on the next frame
Click, hover, value changeAn event goes out and the handler runs in Node. Its changes apply one or two frames later
Hover and pressed looksInk states and styles declared on the node; the engine switches them with no round trip
AnimationAn ink animation (inkanimDefinition) declared on the node and played by the engine
A value every frame, such as a health barA binding the plugin reads each frame, like a declarative rule; or the mod sets the value at its own rate
Keep the game from also acting on a clickA consume flag on the node, applied by the plugin when the event fires

Tier 1 stays optional for later. It is only needed for logic that must run inside the frame, such as custom drawing that depends on frame data. Nothing in the first set of tags needs it.

One tree format, written three ways. In .tsx files the tags are JSX, which TypeScript compiles with REDnode's factory and checks against generated types. Plain JavaScript can write the same tags in a tagged template, or call the functions, which mirror the ui builder. A tree mounts on a layer: hud (display only; hides with the HUD), menu (inside the game's menus, with the game's cursor), and later world (in-world screens through IWorldWidgetComponent). The layers are unverified.

Screens

Besides single widgets, mods need whole screens: open and switch the game's own full-screen menus (inventory, character, cyberware and the rest), and build new ones that behave the same way. A new screen should pause the game, take the game's cursor and Back key, and sit in the hub's row of tabs where that fits. The game does this with two pieces, both in the dump:

PieceWhat it is
Menu resourceinkMenuResource: a list of inkMenuEntry (a menu name, its widget library resource, depth, spawn mode and input context) and the scenario names. Codeware declares both for scripts
ScenariosScripted state machines that open, switch and close menus: MenuScenario_HubMenu (OpenMenu, SwitchMenu, OpenSubMenu, OnBack), plus PauseMenu, Vendor, Storage, Wardrobe, FastTravel and others. inkMenuScenario.SwitchToScenario(name, userData) moves between them
Opening oneA StartHubMenuEvent carrying HubMenuInitData (menuName, submenuName, userData), queued with GetUISystem().QueueEvent. Inside the hub, an OpenMenuRequest. The hub's tabs are the HubMenuItems enum: Crafting, Character, Inventory, Map, Journal, Phone, Database, Stats, Backpack, Codex, Shards, Gallery, Tarot, Gear, Cyberware, VisualSets

Opening and switching the game's screens needs no new engine work. The API wraps these events, so a mod writes ink.screens.open("inventory"). The names map to the game's menu names, kept in one table. Screens that need context, such as a vendor or a stash, take it as an argument or are left out. The plugin also reports the open screen as an event, so mods can follow the player through the menus.

New screens need an entry in the menu resource, because a scenario can only open the menus listed there. The proposal is one generic entry: REDnode adds a single menu, rednode_screen, whose widget is an empty canvas with a REDnode controller. Every package screen opens that one entry, with userData naming the package and screen, and the ink driver builds the package's tree into the canvas. One entry serves every mod, so adding a screen never touches game files. How the entry gets in is unverified and is part of the spike:

Way inNotes
The plugin adds the entry to the loaded menu resourceNo game files changed. Needs the resource in memory before the menu layer reads it
A small REDnode .archive with the canvas widget and a patched menu listThe usual modding route. The widget file can be built with REDbridge (WolvenKit's engine). Patching the menu list may need ArchiveXL
Draw on the menu layer while REDnode holds the game in a menu stateA fallback with no menu entry. Pause, input and Back must then be handled by hand

REDnode's scripts add their own scenario class, extending MenuScenario_BaseMenu, for screens outside the hub. Screens that belong in the hub open as hub menus, and a hub tab can be added by wrapping the hub's controller (MenuHubGameController), as redscript mods do.

Tier 2 · screens (sketch)
ink.screens.open("inventory");                     // a game screen
ink.screens.on("change", (s) => log(s.name));          // which screen is open

const bounties = ink.screen({
  id: "bounties", title: "Bounties",
  hub: { tab: true, after: "Journal" },             // a tab in the hub's row
}, <BountyBoard />);

bounties.open();                                // pauses, takes the cursor and Back
bounties.on("back", () => bounties.close());

Open questions

  • Root: REDnode's own script hook on a HUD or menu controller (base game only), or Codeware's ink system (a requires for ink)? I1 decides.
  • Cursor in gameplay: the HUD layer has no cursor. Options: interactive ink only in menus; the game's cursor shown during Using mode; or REDnode hit-testing its own ink widgets with its cursor.
  • Game library paths can change with a patch. Keep them in one table behind the tags, and check them against the game's files with REDbridge.
  • Should redscript mods be able to find REDnode's ink widgets by name, to place themselves beside them?
  • Screens: which way in for the rednode_screen entry (above)? Can a new hub tab coexist with other mods that wrap the hub? Which game screens can open without context?

07Safety rails for Tier 1

Hard requirement

A buggy interceptor must never crash or freeze the game.

Time budget

Each call is time-limited. On overrun, return to default game behavior.

Fault handling

Catch exceptions, fall back to defaults, and auto-disable an interceptor after repeated failures.

Ordering

Define priority and chaining when several mods hook the same function.

Typed writes

Validate every write to ctx.args against the real parameter types before it reaches the game.

Limited host API

Read-only accessors and shared-memory reads only. No arbitrary game calls from a hook, to avoid reentrancy bugs.

Safe reload

Swap Tier 1 code between frames. Tier 2 reloads freely.

09Roadmap

P0RESEARCH

Map the ABI

Read the RED4ext plugin entry points and the imports and exports of an installed plugin. Inspect how cyber_engine_tweaks.asi hooks and resolves addresses.

P1PROOF

Hello-world plugin

A RED4ext plugin that logs the RTTI class count. Confirms build, load and logging on the current game version.

P2TIER 2

Pipe bridge and Node SDK

Expose one function over a named pipe and call it from Node. Then events, queries, commands and generated types.

P3RULES

Declarative rules

Native fast-path rules applied inside hooks with no IPC. Gives synchronous behavior with no engine.

P4TIER 1

QuickJS interceptors

Add the sandboxed runner, time limits, ordering and fault handling. Only after P2 and P3 show which hooks need it.

10Open questions

  • Full CET-style reflection access, or a smaller curated API for v1?
  • Which hooks must support Tier 1 interception on day one?
  • Implementation language for the native plugin: C++ with RED4ext.SDK, or Rust with red4ext-rs (Audioware is a Rust precedent)?
  • IPC transport: named pipe, local socket, or shared memory for hot data?
  • Packaging: should a Node mod ship inside the usual red4ext/plugins layout or its own folder?
